## 1. Продукт и инфраструктура

**Продукт:** Ender Trails VPN — коммерческий VPN-сервис.

**Уже существующий бэкенд (не трогаем, только используем по API):**
- **Remnawave Panel** — управление пользователями, нодами, подписками.
- **Telegram-бот** (форк Bedolaga) — регистрация, оплаты, рефералка, поддержка.
- **Собственный агрегатор подписок** — прослойка над панелью.
- **Next.js сайт** — лендинг + кабинет.

**Задача приложения:** кросс-платформенный клиент (Flutter), который
авторизует пользователя → получает его подписку → собирает конфиг ядра →
поднимает TUN-туннель → показывает статус/трафик/серверы → ведёт подписку, оплату, рефералку.

## 2. Границы (что НЕ делаем)

- Не переиспользуем код бота/сайта/агрегатора. Общее — только **HTTP-контракт** и **брендинг**.
- Не меняем бэкенд без отдельной задачи. Если нужен новый эндпоинт — фиксируем его в
  `docs/backend-contract.md` как «запрос к бэкенду» и идём реализовывать отдельной задачей.
- Не делаем свой VPN-протокол. Только готовое ядро (sing-box / Xray).
- Не делаем в MVP: свой DNS-резолвер, цепочки прокси, роутинг по доменам из UI,
  wireguard-импорт, десктопные платформы, **iOS**. Платформа на старте — **только Android**.

## 3. Незыблемые правила

### Безопасность
1. **Панель Remnawave недоступна из приложения напрямую. Никогда.**
   Только через наш BFF. `REMNAWAVE_API_TOKEN`, `CADDY_AUTH_API_TOKEN` и любые
   админ-секреты в клиент не попадают — ни в код, ни в `--dart-define`, ни в логи.
2. Секреты времени сборки — `--dart-define-from-file=env.json`. В git только `env.example.json`.
   Секреты времени выполнения (access/refresh токен, hwid) — `flutter_secure_storage`.
3. Ничего секретного в логах, в Sentry breadcrumbs, в `print`. Логгер сам режет
   токены/ключи по маскам.
4. PIN/биометрия на экран ключей (`vless://`) — обязательно.

### Архитектура
5. Feature-first + слои `data / domain / presentation`. Бизнес-логика не живёт в виджетах.
   Виджет не делает сетевых вызовов и не знает о DTO.
6. Любой асинхронный вызов наружу (сеть, ядро VPN, secure storage, платформенный канал) —
   через **интерфейс**, зарегистрированный в DI.
7. Ошибки — `Either<Failure, T>` (`fpdart`). Исключения наружу не пробрасываются.
   Исключения ядра VPN ловятся и превращаются в `Failure` с человеческим текстом.
8. Ключевые сущности — `freezed` + `json_serializable`. DTO ≠ Entity: маппинг в маппере.
9. Состояние: `Riverpod` (`AsyncNotifier` / `Notifier`). `setState` — только для локальной анимации.
10. Навигация: `go_router` + typed routes, один источник правды по роутам.
11. Все строки UI — через `flutter_localizations` (`arb`), RU + EN. Хардкод запрещён.
12. Сгенерированные файлы (`*.freezed.dart`, `*.g.dart`) коммитим — воспроизводимость сборки.

### Процесс
13. Каждый этап заканчивается тремя вещами:
    - `flutter analyze` — ноль замечаний;
    - `flutter test` — зелёный (юнит-тесты на парсеры/мапперы/use-case, golden-тесты на ключевые экраны);
    - запись в `docs/progress.md`: что сделано, что дальше, какие долги.
14. Один этап = одна проверяемая порция. Не начинаем следующий, пока не закрыт текущий.
15. Прежде чем править что-то в ядре VPN — читаем официальную документацию sing-box.
    Прежде чем править интеграцию с панелью — читаем `docs/rw` и официальный контракт.

## 4. Технологический стек (решения по умолчанию)

| Слой | Выбор | Обоснование |
|---|---|---|
| Платформы | **только Android** (iOS/десктоп — после релиза) | решение forsaken |
| Каркас | Flutter (stable), Dart 3 | единая кодовая база |
| State | `flutter_riverpod` + `riverpod_generator` | тестируемо, без BuildContext |
| DI | `riverpod` + `get_it` **не** используем одновременно → только Riverpod | один механизм |
| Навигация | `go_router` | typed routes, deep links, редиректы по авторизации |
| Сеть | `dio` + `retrofit`-генерация или手写 `dio` interceptor'ы | перехват 401 → refresh |
| Ошибки | `fpdart` (`Either`, `TaskEither`) | явная обработка |
| Модели | `freezed` + `json_serializable` | иммутабельность, copyWith |
| Хранилище | `flutter_secure_storage` (секреты) + `isar` (кэш серверов/история) | быстрый локальный кэш |
| Дизайн | Material 3 + `flex_color_scheme`, кастомный ThemeExtension | своя тема, но не борьба с фреймворком |
| Логи/краши | `talker` (логгер) + `sentry_flutter` | |
| Аналитика | свой интерфейс `Analytics`, реализация — заглушка | не привязываться к вендору |
| i18n | `flutter gen-l10n` (ARB) | |
| CI | GitHub Actions: analyze → test → build apk/aab | |
| VPN-ядро | см. `docs/vpn-core.md` | **открытое решение, дефолт ниже** |

**Ядро:**
- `flutter_singbox_client` (sing-box 1.14) — самый быстрый путь до работающего туннеля на Android.
- Ядро спрятано за интерфейсом `VpnEngine`, поэтому миграция на собственный
  `libbox`-плагин (gomobile + pigeon) для iOS/десктопа не ломает ни одну фичу.

**Юридический флаг (важно, решить до публикации):**
- sing-box — **GPL-3.0**; `flutter_singbox_client` — **GPL-3.0**, iOS/Win/macOS/Linux билды у автора — платные.
  Для закрытого коммерческого приложения это проблема: либо открывать исходники приложения,
  либо брать коммерческую лицензию у SagerNet, либо уходить на **Xray-core (MPL-2.0)**.
- Альтернатива: писать свой плагин поверх Xray (`flutter_v2ray_client` как референс, Android-only)
  — MPL мягче (copyleft на уровне файла), но теряем Hysteria2/TUIC/AnyTLS.
- **Решение принимает forsaken.** Я не выбираю лицензирование за него.

## 5. Архитектура (кратко, подробности в `docs/architecture.md`)

```
lib/
  main.dart                     // bootstrap: DI, логгер, Sentry, runApp
  app.dart                      // MaterialApp.router + тема + l10n
  core/
    config/                     // env (dart-define), флейворы
    di/                         // провайдеры, жизненные циклы
    error/                      // Failure, Result, маппинг ошибок
    network/                    // dio-клиент, интерцепторы, ретраи, TLS-пиннинг
    storage/                    // secure + isar обёртки
    logging/                    // talker + маскирование секретов
    utils/                      // форматтеры (байты, даты), extension'ы
  features/
    auth/                       // data | domain | presentation
    subscription/               // получение конфига, статус подписки, трафик
    connection/                 // управление туннелем (главный экран)
    servers/                    // список локаций, пинг, выбор
    settings/                   // kill switch, split tunneling, DNS, язык
    payments/                   // тарифы, оплата (внешняя ссылка/шлюз)
    referral/                   // реферальная программа, промокоды
    support/                    // FAQ, тикеты, контакты
  shared/
    design_system/              // цвета, типографика, кнопки, карточки
    widgets/                    // переиспользуемые виджеты
```

Правило: фича ничего не знает о других фичах. Обмен — через `shared/` или через
интерфейсы в `core/`. Футер `shared/design_system` — единственное место, где живут
цвета, шрифты и базовые «блочные» виджеты.

### 5.1 Брендинг: пиксельный «майнкрафт»-стайл

**Стиль зафиксирован forsaken'ом: «ну типо майнкрафт».** Название `Ender Trails`
идеально ложится на Энд.

Правила стиля (полная версия — `docs/design-system.md`):
1. **Никаких ассетов Mojang.** Шрифт Minecraft, текстуры блоков, звуки — чужая
   интеллектуальная собственность. Только **стилизация**: свой пиксельный шрифт
   (OFL), свои пиксель-арт иконки, своя палитра. Нарушение = бан в сторе.
2. **Шрифт:** `PixCyrillic` (SIL OFL 1.1), уже лежит в `design/fonts/`, полная кириллица.
   Пиксельным шрифтом — заголовки, кнопки, цифры, лейблы. Для длинного текста
   (политика, FAQ) — системный sans: пиксельный шрифт на «простыне» текста нечитаем.
3. **Геометрия:** радиус скругления = 0. Всё прямоугольное. Вместо теней —
   «блочная» фаска: светлая полоса сверху/слева, тёмная снизу/справа.
4. **Сетка:** все отступы кратны 4 (4/8/12/16/24/32) — попадаем в пиксельную сетку.
5. **Анимации:** ступенчатые, без плавного easing. Переходы — дискретные кадры.
6. **Ключевые метафоры:**
   - Главная кнопка подключения — **рычаг** (блок, который физически щёлкает).
   - Индикатор статуса — **лампа из редстоуна** (серая/жёлтая/зелёная/красная).
   - Трафик — **шкала опыта** (зелёная сегментированная полоса).
   - Список серверов — как список миров/мультиплеера: пинг-полоски «уровень сигнала».
   - Загрузка/обновление — **печь**, которая плавит.
7. **Палитра:** глубокий «дипслайт»-фон, изумрудный акцент (connected),
   редстоун-красный (ошибка), золотой (подключение), эндер-фиолетовый (бренд).
   Точные значения в `docs/design-system.md`.

## 6. Интеграция с Remnawave (кратко, подробности в `docs/vpn-core.md`)

Рабочая схема, подтверждённая документацией панели:

1. Приложение авторизуется на **нашем BFF** → получает `accessToken`/`refreshToken` и
   **subscription URL** вида `https://<sub-domain>/<shortUuid>`.
2. Приложение запрашивает конфиг ядра напрямую по subscription URL с суффиксом формата:
   - `GET <subUrl>/singbox` → готовый sing-box JSON
   - `GET <subUrl>/json` → Xray JSON (fallback)
   - без суффикса → зависит от UA-правил панели, **не полагаемся**
3. Заголовки запроса (обязательно):
   - `User-Agent: EnderTrails/<version> (Android; <osVersion>)`
     — **не походить на браузер**, иначе панель отдаст HTML-лендинг.
   - `x-hwid: <стабильный ID устройства>` — если на панели включено ограничение устройств.
     Без него панель вернёт пустое тело + `x-hwid-not-supported: true`.
   - `x-device-os`, `x-ver-os`, `x-device-model` — рекомендуемые, видны админу.
4. Из ответа читаем заголовки:
   - `subscription-userinfo: upload=..; download=..; total=..; expire=..` → трафик и дата окончания
   - `profile-title` (base64), `profile-update-interval`, `support-url`, `profile-web-page-url`
5. Держим fallback-парсер share-ссылок (`vless://`, `vmess://`, `trojan://`, `ss://`,
   `hysteria2://`, `tuic://`) на случай, если BFF отдаёт base64-подписку, а не JSON.

Никаких `Authorization` и cookie на subscription-эндпоинт: он аутентифицируется самим
`shortUuid`, а лишние заголовки ломают кэш прокси.

## 7. Стандарты кода

### Именование
- Файлы: `snake_case.dart`. Классы: `UpperCamelCase`. Приватные поля — без `_` в публичных API.
- Провайдеры Riverpod: `xxxProvider`, нотификаторы — `XxxController` (UI) / `XxxNotifier` (состояние).
- Репозитории: интерфейс `XxxRepository` (domain), реализация `XxxRepositoryImpl` (data).
- Use-case: `XxxUseCase` с методом `call` (или `execute`). Один use-case = одно действие.

### Структура фичи (обязательно)
```
features/<feature>/
  data/
    datasources/     // remote (dio) + local (isar/secure)
    dto/             // freezed + fromJson
    repositories/    // имплементация интерфейса из domain
  domain/
    entities/        // freezed, чистые модели
    repositories/    // абстрактный класс
    usecases/
  presentation/
    providers/       // riverpod-нотификаторы
    screens/
    widgets/
```

### Тесты (минимум на этап)
- Парсер share-ссылок и маппер `subscription-userinfo` → 100% веток.
- Use-case'ы — с моками репозиториев (`mocktail`).
- Критичные экраны (главный экран, онбординг, оплата) — golden-тесты.
- Интеграционный smoke: `FakeVpnEngine` поднимает «туннель» и проверяет переключение состояний.

### UI/UX-принципы
- Главный экран: одна большая кнопка + статус. Всё остальное — на второй план.
- Состояние соединения отображается всегда: `Disconnected / Connecting / Connected / Error / Reconnecting`.
- Никаких «сюрпризов»: до первого подключения показываем системный диалог разрешения VPN
  с объяснением, зачем оно нужно.
- Тёмная тема по умолчанию.
- Офлайн-режим: последнийknown конфиг кэшируется, приложение открывается без сети.

## 10. Решения forsaken'а (зафиксировано 2026-09-01)

| # | Вопрос | **Решение** | Что это значит для кода |
|---|---|---|---|
| Q1 | Платформы | **Только Android** | `flutter create --platforms=android`. iOS/десктоп — не раньше релиза |
| Q2 | Вход | **Через Telegram-бота** | Только `AuthRepository.loginWithTelegram`. Email/пароль **не делаем** |
| Q3 | Конфиги | **Напрямую** с sub-домена | BFF отдаёт только subscription URL; конфиг тянем сами, как описано в `docs/vpn-core.md` §2 |
| Q4 | Платежи | **Сначала в боте, в приложении позже** | Этап E5 сдвинут. В v1 — кнопка «Оплатить» как deep link в бота |
| Q5 | Серверы | **Список серверов — из агрегатора** | `GET /v1/servers` обязателен. Конфиг с sub-домена, метаданные серверов — от агрегатора |
| Q6 | Лицензия ядра | **НЕ РЕШЕНО — блокер** | см. ниже |
| Q7 | HWID/лимит устройств | **«Как в боте будут»** | Не выдумываем свою политику. Шлём `x-hwid` и зеркалим поведение бота. Лимиты уточнить при сверке бэкенда |
| Q8 | Брендинг | **«Ну типо майнкрафт»** | Пиксельный стайл, см. §5.1 и `docs/design-system.md` |
| Q9 | Языки | RU + EN | |

### Единственный блокер: Q6 — лицензия ядра

- `sing-box` — **GPL-3.0** (есть коммерческая лицензия у SagerNet).
- `flutter_singbox_client` — **GPL-3.0**, но Android-билд бесплатный.
- `Xray-core` — **MPL-2.0**, мягче, но нет Hysteria2/TUIC/AnyTLS.

**Практический вывод:** на Android бесплатный билд `flutter_singbox_client` закрывает
всю разработку и тесты. Вопрос встанет ровно один раз — **перед публикацией в стор**.
Там три варианта: открыть исходники приложения, купить лицензию у SagerNet,
или мигрировать на Xray (ядро уже за интерфейсом, миграция = один класс).

Не спорим об этом раньше времени, но и не забываем: напомнить на этапе E6.
